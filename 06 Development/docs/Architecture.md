# SAFR Bali — Architecture

## Назначение документа

Этот файл описывает техническую архитектуру проекта SAFR Bali / Na Bali Team.

Проект строится как Telegram-first экосистема: сначала Telegram-бот и заявки, затем SAFR Club, Mini App, сайт, партнёры, исполнители, выплаты и токенизация.

## Основной принцип

Бот, Mini App и сайт должны работать с одной базой данных и одним backend.

Нельзя делать отдельную логику для бота, отдельную для сайта и отдельную для Mini App. Иначе проект быстро станет сложным для поддержки.

## Мультирегиональная модель

SAFR является общим ботом, а Бали — одним из направлений.

Иерархия интерфейса:

направление → город или регион → услуга.

Видимые направления первой версии:

- Бали;
- Таиланд;
- Россия: Санкт-Петербург, Урал и Кавказ;
- Непал.

Реферальная связь относится к пользователю во всей системе, а не к стране,
городу или первой покупке. Пользователь закрепляется за пригласившим один раз.
Будущие начисления определяются правилами конкретной услуги, но используют
одного и того же пригласившего.

Deep link может открыть конкретное направление, при этом не меняя уже
существующую реферальную связь.

## Маршрутизация обращений и роли

Каждое обращение хранит контекст:

направление → город → раздел → услуга.

Главный админ входит во все маршруты. Остальные менеджеры получают доступ
только к назначенным направлениям:

- `VISA_ADMIN_CHAT_IDS` — только `Бали → Визы`;
- `SPB_MANAGER_CHAT_IDS` — только `Россия → Санкт-Петербург`;
- `THAILAND_MANAGER_CHAT_IDS` — все разделы направления `Таиланд`;
- `MANAGER_CHAT_IDS` — общие обращения без отдельного профильного менеджера.

Назначение сохраняется вместе с диалогом. Проверка назначения применяется к
ответам, истории, внутренним комментариям и эскалации. Добавление нового
профильного менеджера должно выполняться через отдельную переменную окружения
и правило маршрута без изменения общей реферальной системы.

## Курсы валют и отображение цен

Источником курса USDT/IDR служит публичный ticker Indodax. Бот сохраняет последний корректный ответ атомарно в runtime JSON с правами `0600` и при временной недоступности сети использует сохранённое значение.

- карточки виз обновляют курс не чаще одного раза в 3 дня;
- калькулятор обмена обновляет курс по запросу, но не чаще одного раза в сутки;
- эквивалент визовых цен округляется до ближайших 5 USD;
- калькулятор наличных показывает рыночный курс и расчётный курс после вычета 6%.

Финансовая формула и срок кеша задаются в одном сервисе, чтобы карточки и калькулятор не расходились между собой.

## Переходное хранение runtime-данных

Начиная с кандидата v0.5.0 бот использует совместимую dual-write модель:

1. локальный JSON остаётся быстрым fallback и сохраняет все прежние данные;
2. при настроенном `BACKEND_SERVICE_TOKEN` регистрация и события зеркалируются
   через защищённый backend API в PostgreSQL;
3. недоступность backend не блокирует регистрацию, диалог или ответ менеджера;
4. legacy JSON переносится скриптом `scripts/migrate_runtime_to_backend.py`;
5. `source_key` делает повторную миграцию событий идемпотентной.

PostgreSQL-таблица `bot_runtime_events` хранит append-only события:

- сообщение клиента;
- ответ менеджера клиенту;
- внутренняя заметка;
- сообщение внутреннего чата команды.

Это позволяет постепенно сделать PostgreSQL источником правды без опасного
одномоментного удаления production JSON.

## Внутреннее взаимодействие команды

Для каждого клиента существует отдельный staff-thread. Доступ проверяется по
`assigned_staff_ids` и маршруту клиента. Главный админ имеет доступ ко всем
клиентам, профильный менеджер — только к назначенному направлению.

Клиентские ответы и внутренние сообщения разделены разными FSM-состояниями и
обработчиками. Внутренняя заметка или чат:

- никогда не отправляются в chat клиента;
- сохраняются в истории команды;
- уведомляют остальных назначенных менеджеров;
- зеркалируются в PostgreSQL при доступном backend.

### 1. Telegram Bot

Основной интерфейс первого запуска.

Задачи:
- регистрировать пользователя;
- принимать заявки;
- фиксировать рефералов;
- показывать баланс SAFR Points;
- показывать реферальную ссылку;
- показывать QR-код;
- отправлять заявки админу;
- позволять админу менять статусы;
- позволять админу начислять Points.

### 2. Backend

Центральная логика проекта.

Рекомендуемый стек:
- Python;
- FastAPI;
- REST API;
- PostgreSQL.

Backend отвечает за:
- пользователей;
- услуги;
- заявки;
- рефералов;
- SAFR Points;
- правила начислений;
- историю операций;
- админские действия.

### 3. Database

Главное хранилище данных.

Минимальные таблицы:
- users;
- services;
- orders;
- partner_modes;
- referrals;
- reward_rules;
- points_ledger;
- admin_actions.

Главное правило:
points_ledger является источником правды по баллам.

### 4. Telegram Mini App

Адаптивный кабинет внутри Telegram реализован в общем frontend-проекте
`06 Development/web` по маршруту `/mini-app`.

Функции:
- профиль;
- баланс;
- реферальная ссылка;
- услуги;
- заявки;
- статусы.

Mini App отправляет backend исходный Telegram `initData`. Backend проверяет
HMAC-подпись через bot token и срок `auth_date`, после чего возвращает только
данные авторизованного Telegram-пользователя. Service-token и bot token не
попадают в браузер.

### 5. Website

Сайт нужен для доверия, SEO и внешнего трафика.

Первая версия использует ту же frontend-кодовую базу, что Mini App:

- `/` — общая главная SAFR;
- `/mini-app` — кабинет;
- `/privacy` — политика конфиденциальности.

Главная кнопка сайта:
Открыть SAFR в Telegram.

## MVP-фокус

Первый запуск должен решить 5 задач:

1. Пользователь заходит в бота.
2. Пользователь оставляет заявку.
3. Админ видит заявку.
4. Реферал фиксируется.
5. SAFR Points начисляются вручную после подтверждения админом.

## Что пока не делаем

В первый MVP не входит:
- полноценный marketplace;
- автоматические выплаты;
- токен;
- DEX;
- сложная CRM;
- веб-админка;
- SEO-блог;
- мультиязычность.

Эти элементы заложены в Roadmap, но не блокируют первый запуск.

## Future Channel Expansion: VK

MVP starts with Telegram as the main interface.

However, the project should be designed with future multi-channel expansion in mind.

Planned future channels:
- Telegram Bot;
- VK Bot / VK Community messages;
- Website forms;
- possibly WhatsApp / Instagram / email later.

Important architectural principle:

A user is not equal to a Telegram account.

A user is a person/client in the SAFR system. Telegram, VK and other messengers are only communication channels connected to that user.

For MVP, users can be created from Telegram only. Later, additional channel identity tables may be added, for example:

- user_channel_accounts;
- channel_type: telegram / vk / website / whatsapp;
- external_user_id;
- username;
- linked_user_id.

Do not hardcode business logic only around Telegram if it can be avoided.
