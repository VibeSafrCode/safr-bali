# Проверка выпуска SAFRWAY и Yoga Ganster

Обязательный живой чек-лист для каждого выпуска. Основная рабочая беседа отвечает за сбор изменений, точную версию кандидата и проверку результата на адресе пользователя. Git push, сборка и обновление production — разные результаты. Изменение доступа или nginx не означает обновление дизайна.

Редакция 4, 11 октября 2026 года. Этот список дополняет специализированные runbooks, не заменяет разрешение Founder и не расширяет scope.

## Как заполнять

Для каждого релиза сохранить отдельную копию в его `AUDIT/`-пакете с датой, ответственным, scope, точными ревизиями и ссылками на доказательства. Отметки прошлых выпусков не переносить автоматически.

Допустимые состояния: `PASS` — проверено с доказательством; `FAIL` — выявлена ошибка; `NOT_RUN` — не проверено; `N/A` — неприменимо с причиной; `DEFERRED` — явно исключено из этого выпуска с причиной и следующим действием. Незавершённая обязательная проверка не превращается в `PASS`.

## Scope и сохранность

- [ ] Записать, что именно выпускается и на какие URL: основной сайт, Mini App, Admin, бот, Yoga preview или отдельная инфраструктурная настройка.
- [ ] Зафиксировать текущие Git HEAD и реальную deployed revision отдельно; сохранить dirty diff и исключить постороннюю native/Admin-разработку.
- [ ] Сверить актуальные верхние слои README, Current State, Backlog, Decision Ledger, audit entry point и review prompt с новыми receipts. Отделять Git/docs revision от каждой runtime/artifact revision; старые статусы пометить историческими. Для docs-only push доказать отсутствие product diff и не выполнять пустой production redeploy ради совпадения SHA.
- [ ] Указать полный allowlist файлов включённых изменений и список осознанно отложенных задач. Не включать весь dirty worktree.
- [ ] Проверить сохранность утверждённых текстов, переводов, маршрутов, бизнес-идентификаторов и опубликованных цен. Indodax, USD-округление до ближайших $5 и исторические заказы не менять без отдельного задания.
- [ ] Разделить визуальное превью и live-системы: не включать реальные заявки, авторизацию, бота или рассылку как побочный эффект обновления дизайна.
- [ ] При исключении услуги для одного бренда проверить не только меню: прямые RU/EN-страницы, карточки, связанные ссылки, обзорные тексты, FAQ и selector формы. Изменять только бренд-проекцию; исходный SAFRWAY-каталог и действующие цены сохранять. Проверять фактический `404` исключённых страниц на опубликованном адресе.
- [ ] Перед включением live-бота или другого нового потребителя сверить его меню и ссылки с актуальной visibility policy бренда. Static website release не подтверждает готовность frozen bot runtime; такую зависимость явно фиксировать как отдельный gate.
- [ ] Исключить секреты, клиентские данные, private originals, `.env`, dumps, sourcemaps и внутренние receipts из публичных файлов и Git.
- [ ] Проверять весь экспортируемый audit/document archive, а не только добавленный Git diff: старый appendix может содержать private paths. Если нужен только текущий слой, экспортировать его точным excerpt с явным source/export hash и границей, не считать excerpt полным исходником и не переписывать историю автоматически.

## Push и deployment

- [ ] Подтвердить разрешение Founder на конкретный Git/production scope; локальная подготовка не является deploy.
- [ ] Проверить scoped diff и staged paths, выполнить commit/push и записать точный remote SHA.
- [ ] До переключения сохранить предыдущий artifact и конфиги; указать безопасный rollback. Проверить guards текущего состояния, чтобы не затереть чужое обновление.
- [ ] Проверить независимость rollback от повреждённой новой сборки и недоступного transport tar: доверенные закрытые recovery metadata + целый OLD + ожидаемый live target. При повреждённом OLD или сменившемся target — отказ, не принудительная запись.
- [ ] Stage/activate/rollback удерживают общий host-level release lock; остальные известные writers исключены на окно либо используют ту же блокировку. Проверить ошибку сразу после rename по фактической цели symlink, а не только Boolean после возврата функции.
- [ ] До switch проверить внешние URL тем же именованным диагностическим User-Agent и точным URL→local-file mapping. Raw `index.html` может быть закрыт, а `/` открыт; не ослаблять защиту/хеши. Проверять конечный HTTPS host/path, не засчитывать auth/fallback HTML как успех.
- [ ] Выполнить синтаксические проверки конфигов. После reload дождаться готовности новых workers с ограниченным retry; успешная команда reload сама по себе не означает новую версию ответа.
- [ ] Сравнить hashes реально отдаваемых HTML/CSS/JS с новым artifact, а не только существование нового каталога на VPS. Проверить RU/EN и характерные признаки актуального дизайна по **точному адресу, который смотрит пользователь**.
- [ ] Проверить cache headers, redirect/base path и certificate без обхода TLS. При подозрении на старый cache сначала сравнить реальные ответы; не списывать ошибку на браузер без доказательства.
- [ ] Проверить соседние сайты и сервисы: SAFRWAY, Mini App, Quant и другие затронутые соседи. Не отправлять клиентам тестовые сообщения или анонсы без соответствующего разрешения.

## Завершение и обучение на ошибках

- [ ] Дать краткий фактический итог: что доступно, адрес, deployed/artifact revision, проверки, что отложено и как откатить. Не писать «всё готово» при оставшихся обязательных gates.
- [ ] После любой ошибки, упущения, регрессии или замечания Founder **в этом же ходе работы** обновить этот чек-лист и `RELEASE_INCIDENTS.md`: симптом, причина или подтверждённые факты, исправление, новая предотвращающая проверка и её статус.
- [ ] Добавить пропущенную проверку или автоматический guard там, где он соразмерен риску. Не ограничиваться записью «быть внимательнее».
- [ ] До следующего выпуска перечитать незакрытые причины и проверить новые пункты на реальном кандидате. Сохранять историю инцидентов, не подменять первоначальные результаты успешным повтором.
