# Анкета клиента, заявителя и услуги: поля и API

Автор: 05. Дата: 2026-11-10.

Фактический объём выпуска на 16 ноября описан в [записке выпуска](AGENT_VISA_STATUS_RELEASE_20261116.md). Типизированная анкета, общий импорт файлов и доставка остаются частью проекта.

Статус: подготовленный 05 архитектурный контракт для реализации и оценки дельты 01. Founder поручил агентам заполнять анкеты из фото, паспортов, адресов и банковских документов через API, с привязкой к клиенту и услугам. Контракт не является отметкой готовности API или разрешением на произвольную production-миграцию. Текущий статус исполнения и выпуска — только в `CURRENT_STATE.md`.

## 1. Одна система данных

Связи: **CRM-клиент (`User.id`) → заявитель → анкета конкретной услуги → документы и история**.

- Клиент CRM — заказчик/владелец аккаунта. Telegram ID — его внешний идентификатор. Имя владельца паспорта нельзя записывать вместо имени заказчика.
- Заявитель — человек, которому оформляется услуга. Он может совпадать с заказчиком; отдельный Telegram-аккаунт для него не требуется. У заказчика может быть несколько заявителей.
- Одна визовая анкета привязана к существующему `VisaCase.id`, одному заявителю и существующему клиенту. Другие услуги продолжают использовать свои канонические записи, например `LifeService.id`.
- Общие паспортные данные переиспользуются по ссылке на заявителя. Адрес конкретной поездки, сроки, подача и расчёты относятся к услуге. Изменение профиля не переписывает уже поданную анкету или прошлую визу.
- Анкета — типизированные поля. Не создавать универсальный конструктор форм, новую CRM, вторую реферальную сеть или отдельный каталог цен.

## 2. Поля анкеты

Наличие поля в контракте не делает его обязательным для всех услуг. Обязательность задаёт согласованный шаблон конкретной процедуры. Неизвестное значение — `null`/«не установлено», а не догадка.

| Раздел | Поля | Правило |
|---|---|---|
| Привязка | CRM `client_id`, `applicant_id`, `visa_case_id` либо ID другой услуги; версия анкеты | Сервер проверяет связи. Агент не переносит дело между клиентами и не создаёт клиента по одному совпадению имени. |
| Заявитель | Фамилия и имена латиницей отдельно; полное имя как в документе; дата и место рождения; гражданство; пол, если нужен анкете | Значения из паспорта, с указанием источника. Контакты заказчика не становятся контактами заявителя автоматически. |
| Паспорт | Номер, государство выдачи, даты выдачи и окончания, место/орган выдачи при необходимости, ссылка на скан | Чувствительные значения защищены; в списках — маска. Замена паспорта сохраняет прежнюю версию и её связи с услугами. |
| Контакты | Телефон/email заявителя, если действительно нужны процедуре; отдельно контакт заказчика | Не создавать почту, не менять логины/пароли и не сохранять OTP в анкете. |
| Поездка и проживание | Страна, цель поездки, предполагаемая дата прибытия/выезда, адрес проживания, название объекта, регион/город/индекс, ссылка на карту, контакт принимающей стороны при необходимости | Предполагаемая дата прибытия не является фактическим въездом. Для жилья можно ссылаться на существующую услугу аренды; историю поданной анкеты не менять вслед за адресом. |
| Дополнительные сведения процедуры | Профессия/работодатель, принимающая сторона/спонсор, родственники/сопровождающие и документы основания — только если требуются выбранной процедурой | Добавлять явные типизированные разделы по необходимости. Не собирать весь возможный набор персональных сведений для каждой визы. |
| Услуга и подача | Тип услуги/процедуры, существующий тип визы, страна, ID дела/процесса, номер заявления/reference, подтверждённая дата подачи, ответственный, источник наблюдения | Не смешивать номер заявления и номер выданной визы. Только подтверждённая подача попадает в операцию регистрации подачи. |
| Выданная виза | Номер визы, индекс/тип из PDF, дата выдачи, значение и исходная подпись поля «использовать до», указанный срок пребывания, кратность въезда, спонсор, ссылка на PDF | Не выводить кратность/срок из одного названия типа. Срок действия/использования визы, срок пребывания за въезд и дата окончания ITK — разные данные. |
| Фактический въезд и ITK | Дата въезда, номер/документ разрешения на пребывание, подтверждённая дата окончания, продление и его источник; отдельно прогнозные даты | Не вычислять юридическую дату окончания из даты выдачи визы. Прогноз явно обозначается и не заменяет подтверждённую дату. |
| Финансы услуги | Ссылка на существующий заказ/счёт, согласованная стоимость и валюта, подтверждённые платежи, ссылка на чек; отдельно статус платежа на внешнем портале | Использовать существующий учёт. Банковская справка и факт выдачи визы не подтверждают оплату клиентом нашей услуги. Агент не меняет цены, Points или оплату через произвольный PATCH анкеты. |
| Документы | Фото, паспорт, банковская справка, подтверждение проживания, билеты, чеки, готовая виза и иные документы конкретной процедуры | Оригинал, тип, имя, MIME/размер, контрольная сумма, версия, принадлежность человеку/услуге, источник, видимость. Не хранить лишние сведения банковского документа, если они не нужны форме. |
| Передача | Документ готов; отправка запрошена; фактический результат отправки; подтверждение Founder; подтверждение клиента | Принятие файла ботом не означает прочтение или получение человеком. Отправка — отдельное разрешённое действие. |
| Контроль качества | Недостающие поля, конфликтующие источники, вопрос на уточнение, источник каждого заполненного поля, время и автор изменения | История и источники задаются сервером. Молчание не закрывает вопрос и не подтверждает сведения. |

Для банковской справки в анкете достаточно ссылки на оригинал и требуемых процедурой сведений: владелец, дата, банк, валюта и сумма, если эти поля действительно нужны. Реквизиты/операции из документа не превращаются в платёжные команды.

Если процедура связана с внешним иммиграционным аккаунтом, хранить разрешённую ссылку/идентификатор аккаунта отдельно от заявителя и дела. Общий аккаунт подачи не объединяет людей и их права. Логины, пароли и OTP не входят в анкетный API; существующий закрытый доступ к учётным данным сохраняется отдельно.

## 3. Как агент заполняет форму

1. Найти точного клиента в назначенном агенту объёме; определить заявителя и услугу. При неоднозначности спросить, не создавать дубль.
2. Зарегистрировать предоставленные оригиналы в защищённом хранилище или закрытом локальном реестре. Произвольный локальный путь не становится `VisaDocument.storage_key`.
3. Прочитать документы и заполнить черновые поля. Для каждого поля сохранить ссылку на документ/сообщение и статус: внесено из источника, требует уточнения либо подтверждено уполномоченным участником.
4. Проверить полноту и конфликты. Уточнять только отсутствующие/противоречащие сведения. Не заставлять Founder повторно вводить уже извлечённые паспортные поля.
5. Перевести данные в подтверждённое состояние только в пределах разрешений. Юридические даты используют существующие проверки источника и подтверждения; платёж, подача, публикация и отправка — свои отдельные операции.
6. Сохранить результат и прочитать актуальную версию/квитанцию операции. Повтор запроса после обрыва связи не создаёт вторую анкету, дело или документ.

Первый этап не требует собственного серверного OCR/LLM, автоматического доступа к чужим Telegram-аккаунтам или фоновой почте. Документы читают уже работающие агенты; API принимает типизированные данные и файлы.

## 4. API: действующее и предлагаемое

Не выдавать предлагаемые маршруты за уже работающие. Точные имена новых маршрутов закрепить после оценки 01; существующие маршруты сохранить.

| Операция | Контракт | Состояние |
|---|---|---|
| Читать назначенное визовое дело | `GET /api/visa-agent/cases/{case_id}` | Есть; сейчас отдаёт ограниченную проекцию дела/процессов. Полную анкету ещё не отдаёт. |
| Читать анкету | `GET /api/visa-agent/cases/{case_id}/intake` | Предложение: данные, версия, документы, источники, недостающие поля и разрешённые действия. |
| Заполнить черновик | `PATCH /api/visa-agent/cases/{case_id}/intake` | Предложение: типизированный allowlist, `expected_version`, ключ идемпотентности, изменения и ссылки на источники. |
| Приложить документ к анкете | `POST /api/visa-agent/cases/{case_id}/documents` | Предложение: общий существующий механизм защищённой загрузки, allowlist типов, точная область доступа. |
| Зарегистрировать подтверждённую подачу | `POST /api/visa-agent/submissions` | Есть; не использовать для черновика или импорта уже готовой визы без доказательства подачи. |
| Зафиксировать наблюдение портала | `POST /api/visa-agent/processes/{process_id}/observations` | Есть; источник, время, версия, допустимый переход. Не подтверждает клиентскую оплату или передачу PDF. |
| Импортировать готовую визу | `POST /api/visa-agent/cases/{case_id}/issued-document` | Установленный узкий импорт D1. Границы актуальной проверки указаны в записке выпуска. |

Создание/выбор заявителя и черновой анкеты не следует подменять операцией подтверждённой подачи. Для первого этапа назначается существующий клиент/дело; отдельное создание черновика добавляется после описания проверки дублей и назначения области доступа. Контакты и аренда продолжают использовать свои модули, а не визовый endpoint.

Правила записи:

- Сервер выводит клиента и разрешённое дело из проверенного scope. Входной `client_id` не даёт доступ.
- Пропущенное поле не меняется. Явный `null` очищает только поле, которое разрешено очищать. Чужой/неизвестный атрибут отклоняется.
- `expected_version` защищает от перезаписи работы другого агента. При конфликте перечитать данные, не повторять PATCH вслепую.
- Один ключ запроса и тот же payload дают прежний результат; другой payload с тем же ключом — конфликт. Дополнительно проверяется бизнес-дубль дела/документа.
- Не давать общий `PATCH status`. Наблюдение, подача, подтверждение юридических дат, платёж и отправка — отдельные конечные действия.
- Отдельные разрешения на чтение анкеты, черновые поля, загрузку документов, наблюдение статуса и импорт выданной визы. Старые ключи не получают новые права автоматически. Ключи ограничены клиентом/делом, отзывные, с конечным сроком.
- Банковские/паспортные сведения не выдаются агенту аренды автоматически. Ни один ключ анкеты не даёт управление пользователями, ролями, рефералами, Points или секретами.
- Документы проверяются, хранятся защищённо и выдаются после серверной авторизации. Токены, паспортные значения и сырые документы не попадают в Git, AUDIT и журналы ошибок.
- Один файл может участвовать в нескольких разрешённых услугах по явной связи; это не даёт доступ ко всем делам владельца. Переданная анкета/документная версия сохраняется исторически.

## 5. Что уже есть и чего не хватает

Исходная основа проекта `c325195` включает модели и API `visa_lifecycle`, `visa_agent`, `life_services`. Актуальные версии указаны в записке выпуска.

- Есть CRM `User`, визовые дела/процессы, назначение сотрудников, статусы, даты и их подтверждение, события, ограниченные агентские ключи, защищённые документы, уведомления и общие услуги.
- Есть зашифрованный паспортный идентификатор дела, но нет полной общей анкеты заявителя с отдельными паспортными полями и переиспользованием между услугами.
- Номер заявления, номер визы и заявитель требуют явной семантики. HMAC номера для дедупликации не заменяет защищённое читаемое поле номера визы.
- Не хватает типизированного черновика и API его чтения/записи, связи заявителя с заказчиком, происхождения полей и раздельных подтверждений передачи человеком. Это целевая дельта, а не основание переписать действующую CRM.
- Локатор папки на диске — отдельно планируемый механизм. Следовать `CRM_LOCAL_DOCUMENT_LOCATOR_NEXT_2026-10-21.md`; местоположение файла не становится идентичностью клиента/дела.

## 6. Очерёдность и приёмка

1. Завершить ограниченный текущий импорт готовой D1 в подтверждённое существующее дело, с отдельными доказательствами API/production и без отправки клиенту. Его результат не означает готовность общей анкеты.
2. Добавить профиль заявителя и типизированную визовую анкету, привязанные к текущим CRM/услугам. Сначала паспорт/фото/адрес/документы и источники; использовать существующее защищённое хранилище.
3. Разрешить назначенным агентам читать и заполнять черновик через ограниченный API; Founder видит ту же анкету в CRM. Подключение другого агента меняет доступ, не создаёт другой модуль учёта.
4. Расширять конечные операции по подтверждённым сценариям. Автоплатежи, новая публикация, отправка клиенту, произвольные интеграции и общий конструктор не включены автоматически.

Достаточная приёмка общей анкеты: предоставленные документы → заполненные поля с источниками → та же форма в карточке правильного человека/услуги → повтор без дубля; параллельная правка даёт конфликт; чужое дело/поле запрещено; неизвестный платёж/въезд не превращается в подтверждённый. Проверки выполнять на фактических routes и общей логике, без копий бизнес-алгоритмов в тестовых стендах.
